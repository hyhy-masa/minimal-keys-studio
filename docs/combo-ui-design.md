# コンボキー設定 UI設計

## この画面で解決したいこと

キー数の少ない minimal-keys で、複数キーの同時押しに別の動作を割り当て、日常操作を補えるようにする。
「コンボ」を知らない人にも、どのキーを一緒に押すと何が起きるかを、例とキーボード図で理解できるようにする。
登録済み設定の全体像を一覧で把握し、追加・編集・削除を迷わず安全に行えるようにする。
細かな判定条件は初期値のままでも使え、必要な人だけ調整できる段階的な画面にする。

## 前提と確認した契約

### Studioが扱う設定項目

`src/proto/combos.ts` の `ComboConfig` を正とし、画面では次を扱う。

| データ | 画面上の名称 | 表示方針 |
|---|---|---|
| `keyPositions` | 同時に押すキー | 必須。キーボード図から2〜4個選ぶ |
| `binding` | 実行する動作 | 必須。既存の動作選択UIを再利用する |
| `timeoutMs` | 同時押しの受付時間 | 「詳細設定」に置く。初期値50ms |
| `layerMask` | 有効にするレイヤー | 「詳細設定」に置く。複数選択。「すべてのレイヤー」を初期選択とする |
| `slowRelease` | キーを離すタイミング | 「詳細設定」に置く。日本語のSwitchで表す |
| `comboId` | 画面に出さない識別子 | 新規・更新・削除に内部で使用する |

`binding` の内部値（動作IDやパラメーター）、キーの内部位置番号、通信の用語は画面に出さない。

### 件数とキー数の上限

- 1コンボは2〜4キー。4キー上限は既存UIおよびFWの `custom.options` / `ZMK_RUNTIME_COMBOS_MAX_KEYS` と一致する。
- 登録上限は16件。`src/proto/combos.ts` 自体には上限定数がないが、FWの `custom.options` の応答最大数と `Kconfig` の初期値が16である。
- 現在の minimal-keys FW は上限変更をしていないため、UIは「n / 16件」で表示する。実装時はStudio側に共有定数を設け、FW契約変更時に追従できる形にする。

## 採用する構成

「一覧」と「編集フォーム」を縦に混在させず、通常時は一覧、追加・編集時は同じタブ内の編集画面へ切り替える。編集画面は独立したページではなく、上部の「コンボ一覧へ戻る」で元の文脈へ戻れる。

理由は、43キーのキーボード図と動作選択UIを一覧の横や下へ詰め込むと、タブ内で窮屈になり、初心者が今どこを編集しているか見失うため。一方、モーダルは高さ不足や多重スクロールを招くため使わない。

### 一覧状態

```text
┌──────────────────────────────────────────────────────────────┐
│ コンボキー設定                              3 / 16件 [＋追加] │
│ 2〜4個のキーを一緒に押すと、別の動作を実行できます。          │
│ 例: J と K を同時に押す → Esc                                │
├──────────────────────────────────────────────────────────────┤
│ [ J ] ＋ [ K ]  →  Esc                     すべてのレイヤー  │
│ 同時押し 50ms                               [編集] [削除]     │
├──────────────────────────────────────────────────────────────┤
│ [ D ] ＋ [ F ]  →  Tab                     ベース            │
│ 同時押し 60ms                               [編集] [削除]     │
└──────────────────────────────────────────────────────────────┘
```

- ヘッダーに短い説明と具体例を置き、「コンボ」の意味をその場で伝える。
- 件数は追加ボタンの近くに `3 / 16件` と表示し、残り容量を予測可能にする。
- 1件を1枚のカードにし、主情報を「キーの組み合わせ → 実行する動作」の順に大きく表示する。
- 補助情報として、受付時間と有効なレイヤーを表示する。キーを離すタイミングが初期値と異なる場合のみ「すべて離したとき終了」を表示する。
- カード全体を編集ボタンにはせず、明示した「編集」ボタンを置く。削除はゴミ箱アイコン＋アクセシブル名で、確認ダイアログを必須にする。
- 一覧の並びはFWから取得した順を維持する。今回の設計では並べ替え・検索・複製は追加しない。

### 空の状態

```text
┌──────────────────────────────────────────────────────────────┐
│                         [キー2個の図]                         │
│                   まだコンボがありません                     │
│ JとKを一緒に押してEscにする、などの操作を追加できます。       │
│                    [最初のコンボを作る]                       │
└──────────────────────────────────────────────────────────────┘
```

単なる「0件」ではなく、できることが分かる例、2〜4キーという条件、主操作を中央に置く。ヘッダーの追加ボタンは残し、空状態にも同じ追加操作を置く。

### 編集状態

```text
┌──────────────────────────────────────────────────────────────┐
│ [← コンボ一覧]  新しいコンボ                                 │
│ 1. 同時に押すキー                         選択中 2 / 4        │
│    ┌──── 左右分割キーボード図（選択キーをprimaryで強調） ──┐ │
│    └──────────────────────────────────────────────────────┘ │
│    選択中: [ J × ] [ K × ]                                  │
│                                                              │
│ 2. 実行する動作                                              │
│    [ Esc                                      変更する ]      │
│                                                              │
│ ▸ 詳細設定                                                   │
│   同時押しの受付時間 [──●────] 50ms                          │
│   有効にするレイヤー [✓すべて] / レイヤー複数選択            │
│   キーを離すタイミング [Switch]                              │
│                                              [キャンセル][保存]│
└──────────────────────────────────────────────────────────────┘
```

#### 1. 同時に押すキー

- 実機と位置関係が一致する左右分割キーボード図を使う。単純な11列グリッドにはしない。
- キー面にはベースレイヤーの表示名を出す。選択済みは `primary` 背景、未選択は `base-100`、4個選択後の未選択キーは無効表示にする。
- 図の下にも選択済みキーをチップで表示する。視覚だけに頼らず、選択数 `2 / 4` とキー名を読み上げ可能にする。
- クリック／タップで選択・解除する。実際のキーボード入力を待つ方式は採用しない。
- キーごとのタップ領域は44px以上、キーボード図が狭い場合は図全体を縮小せず横スクロール可能にする。

#### 2. 実行する動作

- 既存の `BehaviorBindingPicker` を再利用する。ただし見出しは「実行する動作」とし、選択結果は内部名ではなく「Esc」「レイヤー1へ移動」など利用者向けの表記にする。
- 未選択時は「動作を選ぶ」、選択後は動作の要約と「変更する」を表示する。

#### 詳細設定

初心者が初期値50msのまま保存できるよう、初期状態は閉じる。開いた中は `SettingsCard` と `Switch` の流儀に合わせる。

- **同時押しの受付時間**: 「最初のキーを押してから、残りのキーを押すまでの時間」と説明する。10〜500ms、10ms刻みのスライダーと数値を併記し、「短い／標準／長い」の補助語を表示する。
- **有効にするレイヤー**: 初期値は「すべてのレイヤー」。これを解除した場合のみ、取得済みレイヤー名のチェックボックスを表示し、1つ以上を必須にする。32bitの `layerMask` で表せないレイヤーは選択対象に出さない。
- **キーを離すタイミング**: Switchのラベルは「すべてのキーを離したときに動作を終了」。説明は「オフでは、どれか1つを離した時点で終了します」。内部語 `slowRelease` は出さない。

フッターの「保存」は、キーが2個以上かつ動作選択済みの場合だけ有効にする。無効時も理由をボタン直前に文章で示す。編集キャンセル時に変更があれば破棄確認を出す。

## 主要な操作の流れ

新しいコンボを1つ作るまでをクリック単位で示す。

1. コンボ一覧の「コンボを追加」をクリックする。
2. 「同時に押すキー」のキーボード図で `J` をクリックする。
3. 同じ図で `K` をクリックする。選択表示が `J + K`、選択数が `2 / 4` になる。
4. 「動作を選ぶ」をクリックする。
5. 既存の動作選択UIで「キー入力」を選び、キーとして `Esc` を選択して確定する。
6. 必要な場合だけ「詳細設定」をクリックし、受付時間・有効なレイヤー・キーを離すタイミングを調整する。通常は初期値のままでよい。
7. 「保存」をクリックする。
8. 保存中はボタンを「保存中…」にして二重操作を防ぐ。保存成功後に一覧へ戻し、`J + K → Esc` のカードを表示して成功通知を出す。

読み込みや保存に失敗した場合は入力中の内容を保持し、画面上部に再試行可能なエラーを表示する。接続が失われた場合も編集内容を消さず、保存だけを無効にする。

## 上限に達した状態

- ヘッダーは `16 / 16件` と表示する。
- 「コンボを追加」は無効にし、直下に「登録できるコンボは16件までです。追加するには、既存のコンボを削除してください。」と表示する。
- 既存コンボの編集・削除は利用できる。
- 空きができたら追加ボタンを再び有効にする。
- FWが上限超過を返した場合も、一般的な「保存に失敗」ではなく上限到達の説明に変換する。ただし現行の応答は構造化エラーではないため、実装前に判別方法を確認する。

## アクセシビリティと表示制約

- すべての操作要素は最小44×44px。
- キーボード操作できる要素には `focus-visible` で2pxの `primary` リングと `base-100` のオフセットを付ける。
- アイコンは `lucide-react` の `Plus`、`ArrowLeft`、`Pencil`、`Trash2`、`ChevronDown`、`Keyboard`、`X` を使う。アイコンだけのボタンには日本語のアクセシブル名とTooltipを付ける。
- 色は `tailwind.config.js` の `primary`、`primary-content`、`base-content`、`base-100`、`base-200`、`base-300`、`error` のみを使い、情報の区別を色だけに依存させない。
- ライトモード固定。タブ内ルートは既存同様 `overflow-y-auto` とし、画面全体とフォーム内の二重縦スクロールを作らない。
- キー名、矢印、補助文を組み合わせ、選択状態と結果をスクリーンリーダーでも理解できるラベルにする。

## 既存実装から変えた点と理由

- **11列の均等グリッドを左右分割キーボード図へ変更**: 実機上の場所と画面上のキーを結び付けやすくし、位置番号の誤認を減らすため。
- **一覧と編集フォームの縦混在を状態切り替えへ変更**: 編集対象とフォームの関係を明確にし、大きなキーボード図をタブ幅内で確保するため。
- **一覧カードの情報階層を変更**: 最重要の「キー → 動作」を大きくし、受付時間・レイヤーを補助情報へ下げるため。
- **空状態を説明付きCTAへ変更**: 「コンボ」を知らない人にも用途と次の操作を伝えるため。
- **受付時間を数値入力から説明付きスライダーへ変更**: ミリ秒値の意味を理解しなくても調整結果を予測しやすくするため。
- **`layerMask` と `slowRelease` のUIを追加**: 通信型には存在するのに既存画面では編集できず、読み込んだ値を意図せず保持するだけだったため。
- **上限と残数を常時表示**: 追加を試してから失敗するのではなく、先に制約を理解できるようにするため。
- **44pxタップ領域とフォーカスリングを明文化**: 既存の高さ32pxキーや小さいアイコンボタンを改善するため。

## 既存実装から残した点と理由

- **「キーの組み合わせ → 動作」の表現**: コンボの因果関係を最短で理解できるため。
- **2〜4キーの直接選択**: FW契約と一致し、複雑な入力手順を必要としないため。
- **ベースレイヤーからキーラベルを取得する考え方**: 位置番号ではなく利用者が認識できるキー名を出せるため。
- **既存の `BehaviorBindingPicker` と動作表示ユーティリティ**: アプリ内で動作選択の流儀を揃え、対応する動作の網羅性を維持するため。
- **保存後に再取得して一覧を更新する流れ**: FWが受理・保持した値を表示の正とできるため。
- **削除前の確認ダイアログ、成功・失敗通知、SubsystemUnavailable**: 破壊操作と通信状態を安全に扱う既存の良い仕組みだから。
- **50msの初期値**: protoのデコード初期値およびFW側のフォールバックと一致するため。

## 迷った箇所と選ばなかった案

### キーの選び方

- **採用: キーボード図をクリック**。実機位置と一致し、学習コストが低い。
- **不採用: 一覧／ドロップダウンから選ぶ**。43キーでは探しにくく、左右や隣接関係が分からない。
- **不採用: 実際のキーを同時押しして記録**。初心者には直感的に見えるが、コンボが既に有効な状態での入力競合、Web Serial/BLE越しの押下イベント取得、誤入力時の解除など通信・実装の追加契約が必要になる。今回は既存RPCの範囲を超える。

### 編集画面の置き場所

- **採用: タブ内で一覧と編集を切り替える**。利用可能な幅と高さを最大化できる。
- **不採用: カード直下のインライン編集**。複数カードと大きなフォームが同居し、現在地が曖昧になる。
- **不採用: モーダル／右ドロワー**。キーボード図と動作選択UIには狭く、タブ内とモーダル内で二重スクロールになりやすい。

### 詳細設定の見せ方

- **採用: 折りたたみ**。初回作成に必要な2項目へ集中できる。
- **不採用: 常時表示**。`ms`、レイヤー、キー解放条件が最初から並ぶと、「J + K → Esc」を作りたい初心者の負担が大きい。
- **不採用: 詳細設定を別画面に分離**。1コンボの設定が分散し、保存単位が分かりにくくなる。

## 実装前に解消・検証する事項

- `docs/combo-known-issues.md` ではpacked decode修正が実機未検証のまま。UI復活前に複数コンボの保存・再取得を実機確認する。
- 同文書の接続固着は真因未特定と記載されている。背景説明では通信側解決済みとされているため、実装着手時に最新のFW状態と再開条件を確認する。
- 現行 `src/proto/combos.ts` は最大16件を公開しない。StudioとFWで上限表示がずれない契約方法を決める。
- `layerMask = 0` が「すべてのレイヤー」を意味するか、FW実行側の解釈を実機または実装で確認する。現行モジュールは値を保存・返却するが、提示されたソース範囲では実行時の利用を確認できない。
- runtime-combosモジュールのソースには実行系への接続がTODOと書かれた版が存在する。対象FWでコンボ動作自体が有効であることを実機確認する。
- 保存・削除応答の `success` を現行UIが確認していない。実装時は `error` だけでなく `success` も判定する。
- 新規IDを編集開始時に消費する現行方式は、キャンセルを繰り返すと欠番が増える。保存直前に採番するか、最大値＋1を安全に再計算する。
