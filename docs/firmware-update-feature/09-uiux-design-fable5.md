# 09 UI/UX 詳細設計 — 顧客セルフ・ファーム更新

- 作成日: 2026-07-09
- 作成: Fable 5（プロダクトUX × フロント実装ロール／Studio実コード確認ベース）
- 顧客像: **PC操作に不慣れな場合もあるオフィスワーカー**。専門用語が通じない前提で設計する
- 依頼の核: 「機能だけでなく**見た目もこだわる**」。だから安っぽく見せない・迷わせない
- 前提: `08`（実装）とセット。画面と状態機械は `08 S1.11 / S3.4` に対応
- Studio実UIの出典: `studio-analysis.md`（Tailwind3 / react-aria-components / lucide-react / `light-dark()` oklch色 / GenericModal / Toast）

---

## 0. 設計の背骨（3つだけ覚える）

```
① 顧客は「押すだけ」。成否は目視させず、アプリが物理イベントで自動判定する
   （ボリューム出現＝進む / 消失＝書けた。03 §2.5）
② 1画面に主役は1つ。ボタンは基本1個。迷う余地を作らない
③ 全自動が失敗しても、必ず同じ「手動で押す」画面に落ちる。行き止まりゼロ
```

- この3つは飾りではなく、`08` の状態機械（物理イベント駆動・手動フォールバック常設）がそのままUX原則になっている。**技術設計とUXが一致している**のが強み。

### 1.2 各画面のワイヤーフレーム＋日本語コピー案

すべて Studio既存の `GenericModal`（`<dialog>`・中央モーダル）内に描画。**幅は「既存準拠」では決まらない（Codexレビュー10）**: `GenericModal` 本体は padding/角丸/背景のみで幅制約を持たず（`Studio src/GenericModal.tsx:11-15`）、利用側が `max-w-*` を個別指定する流儀（例: `AppHeader.tsx:77` の `max-w-[50vw]`）。更新Modalは写真/GIFが入るため明示指定する:

- 幅: `w-[min(560px,92vw)]`（デスクトップ上限560px・狭いウィンドウ/mobile幅では92vw）
- 高さ: `max-h-[85vh] overflow-y-auto`（写真+文言で溢れたらModal内部を縦スクロール。背面ページをスクロールさせない）
- 画像: `max-w-full h-auto`（写真A1/A2がModal幅を突き破らない）

## 2. 「更新ボタン」のわかりやすさ

### 2.1 置き場所

| 場所 | 採否 | 理由 |
|---|---|---|
| ヘッダーのメニュー内「ファームウェア更新」 | **採用（入口）** | 年1〜2回の低頻度操作。常時タブを占有しない（`07 §2`）。Studioの `AppHeader` メニュー流儀に一致（`studio-analysis §6`） |
| 常時タブバーに1タブ追加 | 不採用 | 頻度が低く一等地がもったいない。誤クリックも増える |
| 更新がある時だけヘッダーに小バッジ | **採用（気づき）** | 受動的に気づける。Step3で現バージョン取得が可能になってから点灯（`08 S3.3`） |

### 2.2 状態の見せ方（3状態）

```
更新なし:   [ファームウェア更新]          （通常。バッジなし）
更新あり:   [ファームウェア更新 •]        （小さな●ドット。数字は出さない＝威圧感を避ける）
進行中:     メニュー無効＋モーダルが前面   （多重起動をUIでも防ぐ。BusyGuardと二重）
```

- ラベルは「アップデート」等のカタカナ乱用を避け「ファームウェア更新」。ただし初出で「ファームウェア＝キーボードの中身のプログラム」と1行補足（専門用語の即時翻訳）。
- **押し間違え防止**: メニュー内で「設定を初期化」（破壊的）とは**離して**配置し、区切り線で分ける。色も分ける（初期化=控えめ赤、更新=通常）。

### 2.3 モーダル起動後の主ボタン規律

- 1画面=主ボタン1つ（primary）。副ボタン（戻る/あとで）は必ず弱く（ghost/secondary）。
- 破壊的操作（書込中の中止）は色で警告（`08` のキャンセルは書込前のみ有効なので、開始後は物理的に押せない見た目にする）。

## 3. リセットボタンの視覚ガイド（最重要・依頼の核）

「リセットを素早く2回」を、非技術者が**一発で**できるようにする。ここが更新の一番の関門（`03 §8.1①`：顧客はタイミングを掴めない）。

### 3.1 何で見せるか（結論）

```
主役 = 実物写真（該当ボタンを赤丸+矢印でマーキング）
補助 = 動きの短いループGIF/アニメ（「カチカチッ」の2回押しのリズム）
避ける = 抽象イラストだけ（実物と結びつかず、どこを押すか迷う）
```

- **理由**: PC不慣れな人は「図の丸」を実物のどこか探すのに迷う。実物写真に印を付けるのが最短。ただし写真1枚は静止＝「2回・素早く」のリズムが伝わらないので、GIFを重ねる。
- 写真とGIFの二段（静止で場所、動きでリズム）が定番の勝ちパターン（§4のスマホOS更新・ハード製品の初期設定ガイドがこの形）。

### 3.2 R/Lで位置が違う問題

- 右半分と左半分でリセットボタンの物理位置が異なる（`03 U-7`：製品ケースでの位置は実機写真で確定）。
- **画面ごとに「今作業している側」の写真だけを出す**。R作業中はR写真、L作業中はL写真。両方を並べて「どっち？」と迷わせない。
- 見出しに「右半分」「左半分」を大きく色分けで明示（例: R=アクセント青、L=アクセント橙。§5の色トークン）。

### 3.3 画面内の出し方（④の詳細ワイヤー）

```
┌──────────────────────────────────────────────┐
│  ステップ 1 / 2 ： 右半分 の更新    ← 側を色で明示 │
│                                               │
│   「カチカチッ」と 素早く2回 押す               │
│    ┌──────────────────────────┐               │
│    │                          │               │
│    │   [右半分の実物写真]       │  ← 赤丸+矢印  │
│    │      ╲                    │               │
│    │       ●← ここ            │               │
│    │                          │               │
│    └──────────────────────────┘               │
│    [ ▶ 押し方の動画を見る ]  ← GIF/短尺再生     │
│                                               │
│   ● 待機中… 押すと自動で次に進みます           │
│                                               │
│   ▸ ボタンの場所がわからない                    │
│   ▸ 反応しない・うまくいかない                  │
└──────────────────────────────────────────────┘
```

- 「押すと自動で進む」を明記＝顧客は[次へ]を探さない。
- アコーディオン2つ（場所/トラブル）は畳んでおき、困った人だけ開く（情報の段階開示）。

### 3.4 実装時に用意すべきアセット（要件リスト）★発注仕様

| # | アセット | 仕様 | 用途画面 |
|---|---|---|---|
| A1 | 右半分・全体写真（リセットボタン位置） | 真上〜斜め45°・自然光・背景無地・2000px長辺・PNG/WebP・ライト/ダーク両対応（背景透過 or 2版） | ④ |
| A2 | 左半分・全体写真（同上） | A1と同条件・**左半分固有のボタン位置** | ⑦ |
| A3 | リセット箇所の赤丸+矢印オーバーレイ | 写真とは別レイヤー（座標だけ差し替え可能に）。色は§5の警告色でなく誘導色 | ④⑦ |
| A4 | 2回押しループGIF/短尺mp4 | 実物 or 3D。約1.5〜2秒ループ・指がボタンを2回押すリズムが分かる・軽量(≤1MB) | ④⑦ |
| A5 | ケーブル差し替え図（R✗→L🔌） | 簡易イラストで可（場所でなく動作の図なので抽象でOK） | ⑥ |
| A6 | 完了イラスト（任意） | 🎉相当。過剰装飾しない | ⑨ |

- **バンドル方針**: 画像はアプリ内蔵（オフライン更新できるように）。Studio CSPは `img-src` にasset/data:を許容する設計に留める（外部URL画像は避ける。`studio-analysis §3` のCSP方針）。
- **★実装クリティカルパス（Codexレビュー10）**: A1〜A4は「見た目の作り込み」ではなく機能要件。現flasherのbootloaderガイドはテキスト1行だけ（`flasher App.tsx:91-93`）で、写真/GIFはゼロから作る。撮影・赤丸/矢印加工・アプリ内蔵・**ライト/ダーク両テーマでの見え方確認**までを `08 S1.15` の独立タスク（0.5〜1.0日）として計上済み。
- **暫定fallback（実物撮影が遅れる場合）**: 写真が用意できるまでは「キーボード外形の簡易線画＋ボタン位置マーカー＋既存テキスト」で④⑦を先行実装する。写真は差し替え可能なアセット参照にしておく（A3のオーバーレイ分離と同じ思想＝後から実写に差し替えても座標調整だけで済む）。**ただし顧客向けMVPの完了条件は「最終写真アセット実装後の非開発者テスト合格」**——簡易図のままではMVP完了と見なさない（Codexレビュー10 追加提案）。
- **未確定（`03 U-7`）**: 製品ケースでのボタン露出・L側USBポート位置は実機写真1枚で確定してから撮影発注。ship-flash.shが組立済み実機で両方を使う実績から「アクセス可能」と推定だが、撮影前に現物確認。

## 4. 定評あるUI/UXの参照（何を・なぜ）

安易な模倣でなく、minimal-keysの文脈（非技術者・低頻度・失敗が怖い）に合う部分だけ採る。

| 参照 | 何を採るか | なぜ（この文脈で効く理由） |
|---|---|---|
| **ESP Web Tools / 各社Webフラッシャ** | 「1画面1アクション」「進捗は自動・成否はツールが判定」「失敗時に具体的な次の一手を出す」 | 同じ“ファーム書込”ドメインの実績パターン。顧客に技術判断をさせない設計思想が一致 |
| **スマホOSの更新画面（iOS/Android）** | 「ダウンロード→準備→適用の3段の見せ方」「進捗バー＋所要時間の安心感」「更新中は触らせない明確な警告」 | 非技術者が最も慣れている“更新のメンタルモデル”。ここに合わせると学習コストゼロ |
| **ハード製品の初期設定ウィザード（例: スマート家電アプリ）** | 「実物写真＋印＋短尺アニメでボタン操作を教える」二段構え | §3の「場所は写真・リズムはGIF」の勝ちパターンの出典 |
| **Stripe / Linear級のクリーンなオンボーディング** | 「余白の大きさ」「主役1つ」「淡い色調・角丸・上質なタイポ」「達成時の小さな祝福」 | まさかずの要望「見た目もこだわる」に直結。安っぽさを消し“信頼できるアプリがキーボードを触る”印象を作る |
| **モバイル決済/銀行アプリのエラー文言** | 「専門語を使わず、原因より“次にどうするか”を先に言う」 | 失敗が怖い顧客の不安を最短で解消（§6の文言設計の型） |

- 採らないもの: ゲーミング系の派手なアニメ・多色。信頼感を削ぐので不採用（オフィスワーカー向け）。

## 5. デザインシステム（Studio既存との一貫性）

Studioの実トークンに**必ず乗せる**（新しい色を勝手に増やさない。`studio-analysis §6`）。

### 5.1 色（`tailwind.config.js:17-26` の既存トークン）
```
primary / primary-content / secondary / accent /
base-100 / base-200 / base-300 / base-content / success
→ すべて oklch() + light-dark() でOS追従(ライト/ダーク自動)
```
- **★既存トークンの欠落を先に直す（Codexレビュー10）**: Tailwindに定義済みの意味色は `success` のみ（`tailwind.config.js:16-30`）。ところが既存 `Toast` は `bg-error text-error-content` / `bg-info text-info-content` を既に使っており（`Studio src/misc/Toast.tsx:42-48`）、**未定義トークンを参照している**。更新UIで warning/error を使い始める前に、`error / error-content / info / info-content / warning / warning-content` を `light-dark()`+oklch で定義するタスクを実装に含める（既存Toastの表示もこれで初めて正しく色が付く）。
- 更新機能で足す意味色は上記タスクで定義する `warning` / `error`（書込中の「抜かないで」・エラー表示）。
- R/L識別の**アクセント2色**（R=青系 / L=橙系）は既存 accent の濃淡で表現し新規追加を避ける。
- **ダーク/ライト**: Studioは `light-dark()` でOS追従（明示トグルなし。`studio-analysis §6`）。更新UIも同方式＝写真アセットだけライト/ダーク2版を用意（§3 A1/A2）。

### 5.2 タイポ（`tailwind.config.js:12-15`）
- `Inter`（sans）を本文・見出しに。数字（バージョン・%）も Inter。
- キーキャップ表示が要る箇所のみ `keycap` フォント（既存流儀）。
- 見出し大・本文中・注釈小の3段で階層を作る。詰め込まない。

### 5.3 余白・形
- モーダル内は**大きめの余白**（Stripe/Linear級の“呼吸”。§4）。1画面の情報量を絞る。
- 角丸・淡い境界線・影は Studio既存モーダル（`GenericModal`）に合わせる。独自の角張ったカードを作らない。

### 5.4 アイコン（`lucide-react`・既存）
- 🔌=`plug` / ⏱=`timer` / ✓=`check-circle` / ⚠=`alert-triangle` / ●待機=`loader`(回転) を lucide から。絵文字直書きは完了画面の🎉など“お祝い”のみ許容、機能アイコンは lucide で統一。

### 5.5 進捗表示（新規コンポーネント・Studioに無い）
- `ProgressBar`: Tailwindで primary 塗り・base-300 トラック・角丸。% と フェーズ文言（「ダウンロード中/書き込み中/再起動しています」）を上に。
- ダウンロードとフラッシュで**同じ見た目**を使い回す（学習コスト削減）。
- 不定進捗（自動遷移中・§1.3 ④'）は lucide `loader` の回転スピナー。

### 5.6 エラー/成功の演出
- 成功: 既存 `Toast`（success・3秒。`studio-analysis §6`）＋完了画面の🎉。過剰演出しない。
- エラー: モーダル内にインライン表示（トーストで流さない＝読み飛ばされる）。`warning` 色＋ lucide `alert-triangle`＋**次の一手ボタン**をセット（§6）。

## 6. 失敗・リカバリのUX（非技術者が詰まらない）

`08` の状態機械は失敗経路も全て手動フォールバック/リカバリに繋がる。UIはその受け皿を「怖くない言葉」で作る。

### 6.1 文言の型（原因より“次の一手”を先に）

flasherの実装済み文言（`flasher i18n/ja.ts:40-53`）を流用・磨く。顧客の行動が違う3つは必ず区別:

| 状況 | 出す文言（案） | 主ボタン |
|---|---|---|
| ボリューム出ない（`NoBootloaderVolume`） | 「まだ書き込みモードになっていないようです。リセットボタンを**素早く**2回、もう一度押してください。」 | [もう一度試す] |
| 両側挿し（`MultipleBootloaderVolumes`） | 「左右の両方がつながっているようです。**今作業する片方だけ**をUSBでつないでください。」 | [確認した] |
| 別デバイス（`NotUf2Volume`） | 「これは minimal-keys ではないかもしれません。他のUSB機器を外して、キーボードだけをつないでください。」 | [確認した] |
| ダウンロード壊れ（`Invalid/Checksum`） | 「ファームウェアの受信に失敗しました。もう一度お試しください（直らなければサポートへ）。」 | [やり直す] |
| 権限拒否 mac（`PermissionDenied`） | 「書き込みモードのキーボードにアクセスできませんでした。システム設定 → プライバシーで許可が必要かもしれません。」 | [設定を開く方法] |

### 6.2 「押しても反応しない」への追い込みガイド（60秒）

④で60秒ボリュームが出なければ、コピーを自動で強める（`03 §2.5-4`）:
```
● なかなか進みませんね。コツは「カチカチッ」と 0.5秒以内 に2回です。
  ・ゆっくり2回だと反応しません
  ・一度ケーブルを抜いて挿し直すと直ることがあります
   [ 押し方の動画をもう一度見る ]   [ 最初からやり直す ]
```

### 6.3 R/L取り違えのリカバリ（機能的文鎮の救済）

`03 §8.1①`：Rを焼くべき場面でLを焼く等。書込後の検証で検出し**自己修復導線**を出す:
```
┌─────────────────────────────────────────┐
│  ⚠ 取り違えの可能性があります             │
│                                          │
│   左半分に、右半分用のファームウェアが      │
│   書き込まれたようです。                   │
│   下のボタンで正しく焼き直せます。          │
│                                          │
│        [ 正しく焼き直す ▶ ]               │
└─────────────────────────────────────────┘
```
- UF2はブートローダーを壊さないので**焼き直しで必ず戻る**（`03 §2.6`）＝この安心をコピーに込める（「壊れていません。焼き直せます」）。

### 6.4 リカバリモード（常設パネル・§1の⑩）

flasherは「再起動＋サポートリンク」のhonest-minimal止まり（`flasher BUILD_STATE.md:63-64`）。**Studio移植時に3モードとして新規実装する**（`06 C6` の指摘に応える。状態機械・フックの実装設計は `08 S1.12b`。**再スキンではなく新規実装**＝Codexレビュー10 Critical-3）:

```
┌─────────────────────────────────────────┐
│  うまくいかないとき                       │
│                                          │
│   ① いまの手順をもう一度試す               │
│      [ もう一度試す ]                     │
│                                          │
│   ② 片方だけ書き直す                       │
│      焼きたい側:  ( ) 右  ( ) 左           │
│      [ この側を書き直す ]                  │
│                                          │
│   ③ 解決しないとき                         │
│      [ ログを保存 ]  → LINE/Discordへ      │
│   ─────────────────────────────           │
│   最初からやり直す ▸       （小さく常設）    │
└─────────────────────────────────────────┘
```
- 3モードの対応（`08 S1.12b` の状態機械/フックに1:1対応）: ①=`retry_current_step`（recovery突入元stepへ復帰） ②=`flash_one_side(side)`（recovery専用の新規状態3つ+`useRecoveryActions`フック） ③=`export_support_log`（純UIアクション）。末尾の「最初からやり直す」は既存 `RESET`（常設・行き止まりゼロ）。
- **「ログを保存」は実装で確定（Codexレビュー10 Critical-2）**: flasherは文言だけ先行し実体が無かった（`06 C6`：存在しない操作を指示するUI）。Studioでは `support_log_export` を **Step1必須成果物として実装する**（`08 S1.12b`）。保存内容=検出volumes/INFO_UF2全文/manifest version・assets sha/step履歴/FlashError JSON/OS・アプリversion。保存はStudio既存のJSON保存パターン `downloadJson`（`keymap-io.ts:207-219`）流用。
- ②の片側焼き直しは、既にマウント済みボリュームを採用する（`06 W4` の「せっかちな顧客がガイド前にリセット→検出されない」トラップ対策）: baseline=[] で `acquire_bootloader` を呼び、Board-ID一致の既存単一ボリュームをそのまま候補採用（`flasher volume.rs:64-95`）。安全装置（UF2検証/Board-IDゲート）は通常フローと同一経路を通す。

### 6.5 接続切れ・中断（[中止]の具体配線）

- **[中止]の配線は3画面で異なる**（Codexレビュー10: `flash_cancel` はバックエンドのみ存在し、flasherには中止ボタンUI自体が無い `flasher App.tsx:66-68,94-103`。実装タスク=`08 S1.12`/`S1.15`）:

| 画面 | [中止]の状態 | 挙動 |
|---|---|---|
| ③ダウンロード中 | 有効 | UI即時RESET・結果破棄（コアDLは協調キャンセル未対応→裏では完走させキャッシュ破棄。擬似中止） |
| ④⑦ボリューム待機中 | 有効 | `flash_cancel` が待機ループを協調中断 →「中止しました。もう一度いつでも始められます」 |
| ⑤⑧書込開始後 | **disabled化** | グレーアウト（中途半端に止めない）。ホバー時「書き込み中は中止できません」 |

- 書込中の警告: ⑤で常時「⚠ 抜かないで/閉じないで」（`flasher App.tsx:100`）。それでも抜けた場合はUF2非文鎮性で復旧可＝リカバリ②へ誘導。

## 8. まさかず向け・最後のまとめ

- **見た目のキモは3つ**: ①1画面1アクション ②リセットは「実物写真＋印＋2回押しGIF」 ③失敗しても怖くない言葉で必ず次の一手を出す。
- **一番の作り込みどころ**は「④右を書き込みモードに」の画面（§3）。ここが更新の関門。写真とGIFのアセット品質がUX品質を決める。
- **Studioの見た目に完全に合わせる**（新しい色やフォントを増やさない）＝「同じアプリの一部」に見せることが信頼につながる。
- **正直な弱点**: 写真アセットは実機確認してからでないと発注できない（UX-1）。ここが着手の最初のボトルネック。ただし暫定fallback（簡易線画・§3.4）で実装自体は先行できる——**MVP完了の条件だけは「最終写真での非開発者テスト合格」から緩めない**。

## 改訂履歴（2026-07-09・Codexレビュー10反映）

OpenAI Codex 独立レビュー（`10-codex-review-of-detailed-design.md`）の全指摘を反映。まさかず承認済み。

- **GenericModal幅の明示（§1.2）**: 「幅は既存モーダル準拠」は曖昧だった——`GenericModal` 本体は幅制約を持たず（`GenericModal.tsx:11-15`）利用側が `max-w-*` を渡す流儀（`AppHeader.tsx:77`）。写真/GIFが入る更新Modal用に `w-[min(560px,92vw)]` + `max-h-[85vh] overflow-y-auto` + 画像 `max-w-full` を明示指定。

- **support_log_export は実装で確定（§6.4・UX-5解消）**: 「実装 or 文言削除」の二択を「実装」で決着（`08 S1.12b` が成果物定義。`06 C6` 文言先行バグの再発防止）。保存内容と `downloadJson`（`keymap-io.ts:207-219`）流用を明記。
