# ヘッダー再設計（設計書）

- 対象: `src/AppHeader.tsx` を中心とするヘッダー、および関連する `UpdateBanner` / `AppFooter` / `AboutModal`
- 目的: **「隠すな、変化で気づかせろ」** — 更新通知を Mac/Windows の並びに常設し、更新があれば色の変化で気づかせる
- 本書は設計のみ。コード変更は含まない

---

## 1. 設計の結論

### 新しいヘッダー構成（文字図）

**更新がないとき（平常時）**

```
[ロゴ minimal-keysカスタマイズ]   [📶 ● minimal-keys ▼]  [🔋 78%]        [Mac|Windows]  [↶][↷] [💾][🗑]  [⬆][？]
 └ 左: ブランド                    └ 中央: デバイスの「状態」             └ 右: ユーザーの「操作」
```

**更新があるとき**

```
[ロゴ minimal-keysカスタマイズ]   [📶 ● minimal-keys ▼]  [🔋 78%]        [Mac|Windows]  [↶][↷] [💾][🗑]  [⬆●更新あり][？]
                                                                                                  └ 赤ドット＋ラベル付きピルに変化
```

- 📶 = 接続方式アイコン（`Bluetooth` / `Usb`、lucide-react）。緑ドットは現状維持
- 🔋 = 電池残量チップ（分割の左右のうち**低い方**を表示。クリックでバッテリータブへ）
- ⬆ = アプリ更新ボタン（`CircleArrowUp`）。平常時はグレーのアイコンボタン、更新ありで**赤ドットバッジ＋「更新あり」ラベルのピル**に変化
- ファーム更新ボタン（Tauri時のみ表示）は現在の位置（保存/破棄の右）のまま維持

### レイアウトの原則

**中央＝キーボードの状態（接続方式・デバイス名・電池）／右＝ユーザーの操作（表示切替・編集・更新・ヘルプ）。**
状態と操作を混ぜない。この分離が、要素が増えても「どこを見ればいいか」を壊さない支えになる。

### 更新の通知フロー（バナー方式からの置き換え）

| 現状 | 新設計 |
|---|---|
| 起動時1回チェック → バナーを1回だけ表示 → 閉じたら二度と出ない | 起動時＋定期（後述）チェック → **更新がある限りヘッダーのバッジが出続ける**（消せない） |
| 手動確認は About モーダルの奥（気づかれない） | ⬆ボタンのポップオーバー内に「更新を確認」を常設 |

⬆ボタンを押すと小さなポップオーバーが開く:

```
┌──────────────────────────────┐
│ 現在のバージョン: 1.2.3       │
│ ──────────────────────       │
│ （更新あり時）                │
│ 新しいバージョン v1.3.0 が    │
│ 公開されています              │
│ [ダウンロードページを開く]    │
│                              │
│ （更新なし時）                │
│ [更新を確認]                  │
│ → 確認中… / 最新版です /      │
│    確認できませんでした       │
└──────────────────────────────┘
```

- `UpdateBanner.tsx` は**廃止**（役割を常設バッジへ移す。通知機構は1つにする）
- `AboutModal` の「更新を確認」セクションは**撤去**（ポップオーバーへ移設）
- バッジは**ユーザーが消せない**。小さく邪魔にならない形にする代わりに、更新が存在する限り出し続ける。「一度閉じたら気づけない」という現行バナーの構造的欠陥をなくす

## 2. 各要素の採否と理由

| 要素 | 採否 | 理由 |
|---|---|---|
| アプリ更新の常設ボタン＋バッジ | **採用** | 本件の核心。要望どおり Mac/Windows と同じ操作列に置く |
| 接続方式（USB/ワイヤレス）表示 | **採用** | `isWireless` は接続時に既に判明しており（`ConnectModal` → `onTransportCreated`）、App が保持していないだけ。表示コストが極小で「どちらで繋がっているか分からない」を直せる。電池表示の前提情報にもなる |
| 電池残量チップ | **採用（段階実装）** | ワイヤレスが売りの製品で「切れてから気づく」は体験の穴。ただし現行RPCは履歴ストリーム型のみで「現在値だけ」を取る軽量手段がない（§6参照）。Phase 1 は既存RPCの最新エントリ流用、Phase 2 でFW側に現在値RPCを追加 |
| ファーム更新とアプリ更新の統合バッジ | **見送り** | 理由は2つ。(1) **危険度の非対称**: ファーム更新は失敗するとキーボードが使えなくなる操作。安全なアプリ更新と同じ「気軽な赤ドット」に混ぜると、慎重に踏むべき導線の重さが消える。(2) **技術的に成立しない**: `useFirmwareVersion.ts` のとおり、現行出荷FWは `zmk__fwinfo` を公開しておらずインストール済みFWバージョンは常に「不明」。`isUpdateAvailable()` は不明時に false を返す設計（確信がなければ通知しない）なので、統合バッジは実質アプリ更新にしか反応せず「ファームも見てくれている」という誤った印象だけ与える。**将来** fwinfo 対応FWが行き渡ったら、ポップオーバー内に「アプリ／ファームウェア」の2行を並べる形で再検討する（バッジは共有・実行導線は分離） |
| 未保存変更のドットバッジ | **見送り** | 保存ボタンの有効/無効の変化が既にその役割を果たしている。色ドットを増やすと「赤ドット＝更新」の希少性が薄まり、全部が目立たなくなる。**色付きの点はヘッダーに最大2つ（更新バッジ・電池警告）まで**という予算を守る |
| ファーム更新ボタンの位置・形 | **現状維持** | 学習済みの配置を壊さない。ラベル付き（「ファーム更新」）であることが、危険度の高い操作の入口として適切 |
| 使い方（？）ボタン | **現状維持（ヘッダー側に一本化）** | フッター側の重複を削除する（§5） |

## 3. 更新通知の色の選定理由

**結論: バッジドットは `error`（赤）、ボタン本体の強調は `primary`（青）。赤の面積を「点」に限定する。**

- 「赤色みたいに」は**字面どおり赤を採用する**。ただし使う場所を選ぶ
- **赤い「点」は世界共通の通知記号**（iOSのアプリバッジ、macOS Dockの赤バッジ、ブラウザの更新ドット）。点である限り、ユーザーは「お知らせがある」と読み、「エラーが起きた」とは読まない
- 危険なのは**赤い「面」**。ボタン全体を赤で塗ると、保存失敗トースト（error）や破棄操作と同じ文法になり「何か壊れた」と誤読させる。だから赤はドット（約8px、白フチ付き）に限定する
- ボタン本体の強調は `bg-primary/10 text-primary`（アクティブタブと同じ文法）＋ラベル「更新あり」。青はこのアプリの「選択されている・アクションできる」の色として既に学習されている

検討して落とした案:

| 案 | 落とした理由 |
|---|---|
| `error` でボタン全面を塗る | 上記のとおり「壊れた」と誤読される。破棄(🗑)の隣に赤い面があるのは事故のもと |
| `warning`（黄） | 明度80%と高く白背景で埋没する。かつ「注意・危険予告」の意味で、良い知らせに合わない |
| `success`（緑） | 接続ドットが既に緑。ヘッダー内で緑が2つになると接続状態の一意性が壊れる |
| `primary` のみ（ドットなし） | ヘッダー下のタブにも primary が多用されており「変化」として弱い。まさかずの却下理由（変化がないと気づかない）に再び抵触する |

つまり「赤色みたいに」の**意図（強く気づかせる）と字面（赤）の両方**を、赤を通知記号の文法（ドット）に閉じ込めることで同時に満たす。

## 4. 更新があるとき／ないときの見た目の違い

| 状態 | ⬆ボタンの見た目 | 挙動 |
|---|---|---|
| 更新なし | アイコンのみ（`CircleArrowUp`、`text-base-content/50`）。？ボタンと同じゴースト調 | ツールチップ「更新を確認」。クリックでポップオーバー（現在バージョン＋手動確認） |
| 確認中 | 同上（変化なし。チェックはバックグラウンド） | — |
| **更新あり** | **ピル化**: `bg-primary/10 text-primary font-medium`＋ラベル「更新あり」＋アイコン右上に `bg-error` の8pxドット（`ring-2 ring-white` で白フチ） | クリックでポップオーバー（新バージョン番号＋「ダウンロードページを開く」）。バッジは更新が解消するまで消えない |
| 確認失敗（オフライン等） | 平常時と同じ | ポップオーバー内の手動確認で「確認できませんでした」を表示（バッジは出さない。不確かな情報で赤を点けない） |

- 出現アニメーションは**1回だけの軽いスケールイン**（例: 200ms）。点滅・常時パルスは長時間使う道具では騒音になるので禁止。`prefers-reduced-motion` ではアニメーションなし
- 色だけに頼らない: ラベル「更新あり」の文字が非色覚的な手がかりを兼ねる。`aria-label="アプリの更新があります"` を付与

電池チップの状態変化（同じ思想で「平常時は無彩色」）:

| 残量（低い方の半分） | 見た目 |
|---|---|
| 31%以上 | `text-base-content/70` の無彩色（数値＋アイコン） |
| 30%以下 | `text-warning-content bg-warning/20` のチップ化 |
| 10%以下 | `text-error` ＋ `BatteryWarning` アイコン |

## 5. 全体の整理（フッター・About）

**フッター（現状）**
`© 2024 - The ZMK Contributors - About ZMK Studio - License NOTICE - 使い方を見る`

**フッター（新）**

```
minimal-keys カスタマイズ v1.2.3 ｜ このアプリについて ｜ ライセンス
```

- 「使い方を見る」を**削除**（ヘッダーの？と完全重複。ヘルプの入口は1つにする）
- 製品名を minimal-keys に改める。上流の名前・著作権表記は消すのではなく **「ライセンス」（License NOTICE モーダル）と「このアプリについて」内の ZMK クレジットに移す**。OSSの帰属表示義務はモーダル側で満たす
- バージョン番号（`CURRENT_APP_VERSION`）をフッター常設にする。サポート問い合わせ時に「今のバージョンは？」に即答できるようになり、更新ポップオーバーの現在バージョン表示とも整合する

**AboutModal**

- 「更新を確認」セクションを撤去（ヘッダーのポップオーバーへ移設済みのため）
- 冒頭の ZMK Project リンク群・スポンサー壁は上流のままなので、「minimal-keys のアプリ紹介＋ Powered by ZMK Studio ＋スポンサー謝辞」への再構成を推奨（本設計のスコープ外。別課題として起票する）

## 6. トレードオフ（何を優先し、何を犠牲にしたか）

**優先したもの**

1. **気づく変化**（本件の核心）: 更新バッジを常設・不可消去にし、平常時のヘッダーを無彩色に保つことで「変化した瞬間」のコントラストを最大化した
2. **状態の可視化**: 接続方式・電池という「知らないと困るのに隠れていた情報」を一等地へ
3. **学習済み配置の維持**: OS切替・元に戻す・保存・破棄・ファーム更新の位置と挙動は一切動かさない（`data-tour` 属性も維持）

**犠牲にしたもの**

1. **ヘッダーの密度が上がる**（要素+3: 接続方式アイコン・電池チップ・更新ボタン）。緩和策として (a) 平常時は全て無彩色・小型、(b) 色付きの点は最大2つまでの予算制、(c) バナー廃止で縦方向はむしろ1行減る
2. **更新バナーの「文章で説明できる面積」を失う**。バッジ＋ポップオーバーは一手間増える。ただし「一度閉じたら終わり」の欠陥除去のほうが重い
3. **ファーム更新の統合を見送った**ため、将来 fwinfo 対応FWが普及した時にポップオーバーの再設計が必要。これを見越して、ポップオーバーの中身は「行（アプリ／将来ファーム）」の縦積み構造で実装しておく
4. **未保存インジケータ等の追加情報は載せない**。色の希少性（＝更新バッジの目立ち）を守るための意図的な取捨

**うまくいかない可能性と対策（批判チェック）**

| 懸念 | 対策 |
|---|---|
| 赤ドットが小さすぎて気づかれない | ドット単体ではなくピル化＋「更新あり」ラベルとの複合で面積を確保。実機スクリーンショットで まさかず確認を必ず挟む |
| 電池の現在値取得が重い／取れない | Phase 1 は接続時に既存の履歴RPCを1回だけ叩き最新エントリのみ採用。エントリ数が多く実測で遅い場合は Phase 2（FW側の現在値RPC）まで表示を見送る判定を先に置く |
| バッジが消せないことを鬱陶しく感じる | ピルは小さく無音（点滅なし）。それでも不評なら「このバージョンをスキップ」をポップオーバー内に追加する余地を残す（`NOTIFIED_VERSION_STORAGE_KEY` を転用可能） |

## 7. 実装時の注意点

### データ経路の変更

| ファイル | 変更内容 |
|---|---|
| `src/App.tsx` | (1) `onConnect` で受けている `isWireless` を state に保持し `AppHeader` へ渡す。(2) `availableUpdate` を `AppHeader` へ渡す（`UpdateBanner` レンダリングは削除）。(3) 更新チェックを起動時1回→起動時＋24時間ごと（または window focus 時にスロットル付き）に拡張 |
| `src/AppHeader.tsx` | 接続方式アイコン・電池チップ・更新ボタン＋ポップオーバーを追加。既存ボタン群と `data-tour` 属性は不変 |
| `src/update/versionCheck.ts` | `checkForUpdate` が「最新版」と「確認失敗」をどちらも `null` で返す現仕様のままだと、手動確認で「最新版です」と正直に言えない。戻り値を `{ status: "latest" | "available" | "error", release? }` の3値に拡張する |
| `src/update/UpdateBanner.tsx` | 削除（stories・参照含む） |
| `src/AboutModal.tsx` | 更新確認セクションを削除 |
| `src/AppFooter.tsx` | §5の構成に変更。`onStartTour` prop を削除 |

### 電池表示（Phase 1）

- `zmk__battery_history` サブシステム（`src/proto/battery.ts`）には `getHistory` / `clearHistory` しかない。現在値は履歴の最新エントリから取る
- バッテリータブ（`BatteryHistory.tsx`）が既に接続時自動フェッチを持つが、**タブは開かれるまでマウントされない**。ヘッダー用に取得ロジックをフックへ切り出し（例: `useBatteryLevels`）、ヘッダーとタブで共有して**二重フェッチを防ぐ**
- 分割キーボードは `sourceId` ごと（左右）に電池がある。ヘッダーは低い方を表示、クリックでバッテリータブへ遷移
- `BatteryHistory.tsx` の色は生hex（`#22c55e` 等）で書かれており本設計の制約（トークンのみ）に反する。ヘッダー側は必ず `success`/`warning`/`error` トークンを使う。既存hexの置き換えは別課題（承認を得てから）

### スタイル・アクセシビリティ

- 色は `tailwind.config.js` のトークンのみ（`primary` / `error` / `warning` / `base-*`）。生hex禁止
- 新設ボタンは `min-h-11 min-w-11`（44px。ヘッダーは h-12=48px なので収まる。`UpdateBanner` の既存ボタンが同じ作法）
- フォーカスリング: `focus-visible:outline focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-primary` を全新設ボタンに
- 内部用語を出さない: 「RPC」「サブシステム」「BLE」は使わず「ワイヤレス」「USB」「更新」で統一（`ConnectModal` が既に「ワイヤレス/USB」の語を使用しており整合）
- ポップオーバーは `react-aria-components` の `MenuTrigger`/`Popover`（デバイスメニューと同じ部品）で実装し、Esc/外側クリックで閉じる標準挙動を得る

### 壊してはいけないもの

- `data-tour="os-toggle" / "undo-redo" / "save-discard"` は `src/tour/steps.ts` が参照。属性を落とすとツアーが壊れる
- `AppHeader.test.tsx` / `AppFooter.test.tsx` / `AppHeader.stories.ts` / `UpdateBanner.stories.tsx` の更新が必要
- `fwUpdateOpen` の持ち上げ（F-6: ファーム更新中に ConnectModal を重ねない制御）に触らない
- 更新ポップオーバーを開いたままファーム更新モーダルが開くケース → ポップオーバーは軽量なので `fwUpdateOpen` 時に閉じるだけでよい

### 実装順の提案

1. 更新ボタン＋バッジ＋ポップオーバー（本件の核心。バナー廃止・About移設まで含めて1コミット群）
2. 接続方式アイコン（`isWireless` の保持と表示のみ。小さい）
3. フッター整理
4. 電池チップ（Phase 1。実測でエントリ数と取得時間を見てから出す）
